# jiko-bundler

Сборщик Python-исходников в один **обычный читаемый файл**: `.py`, `.pyp`
или другое расширение. Не зависит от Cinema 4D или другого DCC.
Не добавляет `exec`, архив, строки с исходниками, временную распаковку
или загрузчик модулей. Зависимостей вне стандартной библиотеки нет.

Это статический сборщик для кода, подготовленного к общему пространству имён,
а не универсальная замена Python import system. Произвольный Python-пакет
не всегда можно корректно превратить в плоский файл. Ограничения перечислены ниже.

## Установка

Из корня репозитория:

```console
python -m pip install -e packages/jiko-bundler
```

## CLI

```console
jiko-bundle path/to/entry.py -I path/to/sources -o dist/plugin.pyp
```

Или `python -m jiko_bundler` с теми же аргументами.

- `-I / --python-path` — корень поиска локальных модулей; можно повторять.
  Указывается каталог **над** пакетом, например `packages/jiko-bridge-client`.
  Каталог точки входа также включается в поиск.
- `--external c4d --external maxon` — сохранить указанные модули и их подмодули
  внешними, даже если в путях поиска есть их исходники или заглушки.
- `--strip-docstrings` — убрать docstring функций и классов и описание секций.
- `-o / --output` — выходной файл; расширение не влияет на сборку.
- `--version` — версия сборщика.

Исходники во время сборки **не выполняются**: DCC и его SDK не нужны.
Модули, отсутствующие в указанных корнях, остаются внешними импортами.
Сборщик не ищет зависимости автоматически в `site-packages` и не включает
Python-интерпретатор, бинарные расширения или ресурсы.

Безусловные внешние импорты уровня модуля автоматически собираются в блок
в начале результата. Повторы удаляются с учётом `as`, а импорты символов
из одного модуля объединяются: `from typing import Any, Optional, List`.
Разные подмодули (`urllib.error`, `urllib.request`) сохраняются отдельно.
Группы идут в порядке первого появления, без алфавитной сортировки.
Вложенные импорты остаются в своих функциях/классах/условиях и не участвуют
в этой дедупликации. Условные импорты уровня модуля по-прежнему отклоняются.
Внешние импорты теперь выполняются перед кодом всех секций: настройку,
которая должна предшествовать импорту, нужно делать вне собираемого файла.

Готовый файл синтаксически проверяется перед записью. При ошибке сборки
предыдущий файл сохраняется. Перезапись входного исходника запрещена.

## Python API

```python
from jiko_bundler import bundle, bundle_to_file

result = bundle(
    "path/to/entry.py",
    search_paths=["path/to/sources"],
    external=["c4d", "maxon"],
)
print(result.source)
print(result.modules)  # Абсолютные пути исходников в порядке включения.

bundle_to_file(
    "path/to/entry.py",
    "dist/plugin.pyp",
    search_paths=["path/to/sources"],
    external=["c4d", "maxon"],
    strip_docstrings=True,
)
```

Ошибки преобразования имеют тип `BundleError`. Ошибки файловой системы —
`OSError`. CLI перехватывает их и завершает работу с кодом `1`.

## Пример

`helpers.py`:

```python
def greeting(name):
    return f"Hello, {name}!"
```

`entry.py`:

```python
from helpers import greeting

if __name__ == "__main__":
    print(greeting("Jiko"))
```

После сборки в файле будут определение `greeting` и код точки входа.
Внутренний импорт исчезнет. Также поддерживается `import helpers as helper`
с обращением `helper.greeting(...)`: оно превращается в `greeting(...)`.

Готовый пример в репозитории:

```console
python -m jiko_bundler packages/jiko-bundler/examples/entry.py -o dist/bundler-example.py
```

## Правила подготовки модулей

- Локальные импорты должны быть статическими, безусловными и на уровне модуля.
  Поддерживаются абсолютные и относительные импорты, явные реэкспорты и алиасы.
  Вложенные/условные импорты локальных модулей и `import *` отклоняются.
- Все определения попадают в общее пространство имён. Разные функции,
  константы и классы с одинаковым глобальным именем — ошибка.
  Повторные импорты одного символа разрешены. Имена не переименовываются
  автоматически, поэтому результат остаётся читаемым.
- `module.symbol` преобразуется статически. Передавать локальный модуль
  как объект, менять его атрибуты, затенять его алиас параметром функции
  или ссылаться на алиас в строковой аннотации нельзя.
- Циклы импортов отклоняются. Неявно подключаемые `__init__.py` должны
  содержать только импорты, docstring и неиспользуемые литеральные метаданные
  `__all__` / `__version__`. Эти метаданные зависимостей удаляются из результата;
  импортировать их как символы нельзя. Инициализацию вынесите в отдельную функцию.
  Namespace packages не поддерживаются.
- Модули зависимостей предназначены для определений. Код с важным порядком
  побочных эффектов при импорте вынесите в функции и вызывайте из точки входа:
  сборщик размещает зависимости перед использующим их модулем.
- Динамические импорты, `exec`, `eval`, инспекция пространств имён,
  зависимости от `__file__`, `__package__`, `__spec__` и аналогичных атрибутов
  не поддерживаются. Типовые прямые и алиасные вызовы отклоняются;
  произвольную косвенную динамику статический анализ доказать не может.
- `if __name__ == "__main__"` сохраняется только в точке входа.
  В подключённых модулях остаётся его ветка `else`, если она есть.
- Обращения к `__name__` в зависимостях заменяются исходным именем модуля,
  поэтому имена логгеров сохраняются.
- В модулях с `from __future__ import annotations` аннотации преобразуются
  в строки, а сам future-импорт удаляется. Режим остальных модулей не меняется.
  Остальные future-флаги не поддерживаются.
- AST нормализует форматирование и убирает исходные комментарии. Docstring
  сохраняются (описания модулей становятся комментариями секций), если
  не передан `--strip-docstrings`. Лицензии из комментариев нужно переносить
  в распространяемые файлы отдельно.
- `__module__` классов и функций будет принадлежать выходному файлу.
  Код, завязанный на pickle, рефлексию, `sys.modules` или hot reload отдельных
  модулей, требует адаптации. Это не сборщик dev-загрузчиков.

Собирать нужно Python-версией, совместимой с целевым DCC. Сборщик не понижает
версию синтаксиса и не проверяет доступность внешних API в приложении.

Cinema 4D уже использует этот пакет:

```console
make pkg-package-c4d
```

Команда запускает `packages/jiko-bundler/bundle.py` прямо из репозитория;
устанавливать сборщик для этой make-цели не нужно. Выходной файл —
`dist/cinema4d/jiko_bridge_c4d.pyp`. В сборку попадают C4D-пакет и общий
клиент. Dev-контроллер `jb_development.py` не включается.

Для разработки подключите `plugins/cinema4d-dev` из репозитория в путях
плагинов Cinema 4D и отключите release-копию. После однократного перезапуска
можно редактировать исходники и нажимать **Jiko Bridge → Reload**.
`jb_plugin.py`, `jb_development.py` и dev-точка входа остаются постоянными;
их изменения требуют перезапуска C4D. Ошибка импорта при Reload восстанавливает
старые модули и выводит traceback в Python Console. Побочные эффекты импорта
автоматически не отменяются. В релизном bundle Reload отключён.
